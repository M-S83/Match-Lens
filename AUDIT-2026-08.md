# Match Lens — Audit, August 2026

Whole-repo audit: 43 Python modules (~21,900 LOC) plus `SKILL.md` (4,874 lines).

---

## Verification tiers

Findings are split by how strongly they are evidenced. This distinction is the
point of the document — the previous audit's headline findings had gone stale
without anyone noticing, so provenance is tracked explicitly.

- **CONFIRMED** — re-derived by reading the cited code directly during this audit.
  Every quote checked against the working tree.
- **REPORTED** — surfaced by a systematic sweep with file:line evidence and a
  traced failure path, but not independently re-derived. Treat as high-quality
  leads: verify before fixing.

No match data, video, or installable environment exists here, so **the pipeline
cannot be executed**. This is static analysis throughout — findings are argued
from code paths, never from a reproduction run.

Two candidates that did not survive verification were **dropped**, not downgraded
and kept. They are listed at the end so a future audit does not re-raise them.

---

## Summary

The pipeline's correctness machinery is largely **written but not wired**.

Three independent systems that exist to keep the analysis honest are inert:
the readiness gate is never read (**A1**), the evidence-tier and result-family
gating operates on an array that is always empty (**A2**), and two published
per-player metrics are constants computed from a field the spec forbids (**A3**).

Separately, several metrics **ship a provenance string that states a formula the
code does not implement** (**A5**, **A6**) — so the discrepancy is invisible in
both `deep_skill_metrics.json` and the report's methodology text.

The root cause is structural: `SKILL.md` governs 13 pipeline steps but names only
8 of 43 scripts, so spec and code can drift with nothing to detect it (**A11**).

# CONFIRMED

## A1 — `report_ready: false` does not stop report generation

**Severity: CRITICAL.**

`SKILL.md:2823` states the interlock in the strongest terms the spec uses:

> **Hard rule:** If `report_ready` is `false`, Step 4 does not run.

repeated at `SKILL.md:3600` and `SKILL.md:4812`. **No code enforces it.** A
repo-wide grep for `report_ready` returns hits in exactly one file —
`build_readiness_check.py`, which computes and writes it. Zero readers elsewhere.

The gate runs as step `3j_readiness` (`pipeline_runner_v2.py:2698`); its return
value is discarded by the generic step runner:

```python
func(match_dir)
mark_step(match_dir, state, step_id, "complete")   # :2349-2350
```

Control falls into `# ── PHASE 5: Reports ──` (`:2712`) — tactical report (`:2731`),
opposition report (`:2751`) — and `PHASE 6` (`:2807`) — flagged moments, pass
network. Phase 5 *does* load `report_readiness.json` (`:2923`, `:3035`) but reads
only `player_id_ceiling` from it.

**Failure:** boundary confidence 0.4, 12 of 20 windows complete → `report_ready:
false`, `[X]  NOT READY` prints, `False` returned and dropped, step marked
`complete`, all four reports generated and delivered carrying normal confidence
language. The mechanism the system relies on to avoid shipping unsupported
analysis never fires.

## A2 — the entire evidence-gating system operates on an empty array

**Severity: CRITICAL.**

`SKILL.md:1291` mandates the Universal Finding Object: *"Every finding produced by
agents must carry these fields"* — `finding_type`, `subject_player_id`,
`subject_player_label`, `supporting_frames`, `opposition_focus_type`,
`result_family_status`, `evidence_tier`.

**None of those field names appears in any `.py` file in the repo** (verified: 0
occurrences). The actual Tier-1 agent output schema (`pipeline_runner_v2.py:441-561`)
has no `findings` array at all — `grep -c '"findings"' pipeline_runner_v2.py` = **0**.

Yet `merge_utils.py:251-252` is built entirely around it:

```python
a["findings"] = stamp_gates_on_findings(
    a.get("findings", []), gates, source_note
)
```

**Failure:** `a.get("findings", [])` is always `[]`, so `stamp_gates_on_findings`
runs over an empty list on every window of every match. `SKILL.md:1320-1321`
("The pipeline stamps `result_family_status` and `source_type` from
`result_family_gates.json` after each window is merged") describes something that
never happens. Every source-limitation rule keyed off a finding's family is inert,
and report writers receive unqualified observations with no evidence tier and no
limitation note — the opposite of the pipeline's stated discipline.

## A3 — two published player metrics are constants, from a field the spec forbids

**Severity: CRITICAL.**

`deep_skill_metrics.py:1611`

```python
by_player[pid]["ratings"].append(obs.get("rating", 3))
```

`"rating"` occurs in **exactly one place in the entire repository** — that default.
No schema, no prompt, no agent emits it. And `SKILL.md` explicitly forbids it:

> `SKILL.md:1630` — "Describe what you saw specifically -- no evaluation, no ratings"
> `SKILL.md:4196` — "No ratings. No evaluation. No comparison to ideal performance."

So every observation contributes a fabricated `3`. With all ratings identical,
`var = 0.0` and `avg_r = 3.0`, giving for **every player in every match**:

- `player_role_consistency = round(1.0 - 0/4, 2)` = **1.00** ("perfectly consistent")
- `player_positioning_stability = round(3.0/5.0, 2)` = **0.60**

Emitted at `:2463-2469` with `evidence_tier="repeated_pattern"` and confidence ≈0.7.
The `if not ratings: continue` guard at `:1616` never fires, because the default
fabricates a value per observation. These are not degraded measurements — they are
constants presented as per-player findings.

## A4 — ground truth validation scores every event as missed

**Severity: HIGH.**

`ground_truth.py:102` reads `moment.get("timestamp", "")`. `key_moments` entries
do not carry `timestamp` — the agent schema emits `minute`
(`pipeline_runner_v2.py:540`), and `merge_utils.py:400-403` states the live
contract:

```python
# Accept both "timestamp" (legacy) and "minute" (Fix 32a schema) keys.
return m.get("timestamp") or m.get("minute") or ""
```

`ground_truth.py` reads the legacy key **only**, with no fallback, so it receives
`""` for every moment, `seconds_match(x, "")` is always `False`, and every known
event scores *missed*.

**Failure:** the pipeline correctly detects all 3 goals; `ground_truth_check.json`
reports `missed: 3`. The event-validation layer is blind and reports a perfect run
as a total failure.

## A5 — `build_up_route_diversity` divides by 4 while reporting `/12`

**Severity: HIGH.**

| | |
|---|---|
| `SKILL.md:3225` | "Distinct zone-to-zone route pairs / **12** (recalibrated ceiling)" |
| `deep_skill_metrics.py:1444` | `score = round(min(len(zone_pairs) / 4.0, 1.0), 2)` |
| `deep_skill_metrics.py:2372` | emits `calculation_basis`: `"Distinct zone-to-zone route pairs / 12 (recalibrated ceiling)"` |

Diversity saturates at 1.0 from **4** distinct routes instead of 12. Because
`calc_predictability` (`:1453`) is `pattern_reliability*0.6 + (1.0 - route_diversity)*0.4`,
almost any match with ≥4 route pairs is scored maximally *unpredictable*:
`predictability_score` is deflated by up to 0.4 and the `highly_predictable`
category (≥0.75) is effectively unreachable.

The `calculation_basis` field is provenance shipped to the report writer — it
asserts the spec formula, so the divergence is invisible downstream.

## A6 — `compactness_score` uses different weights *and* measures a different quantity

**Severity: HIGH.**

| | |
|---|---|
| `SKILL.md:3208` | "Line height **stability** (60%) + pressing intensity (40%)" |
| `deep_skill_metrics.py:1069-1070` | `# 80% line height position, 20% pressing activity`<br>`score = round(height_score * 0.80 + press_norm * 0.20, 2)` |
| `deep_skill_metrics.py:2267` | emits `calculation_basis`: `"Line height stability (60%) + pressing intensity (40%)"` |

Two divergences at once. Pressing contributes **half** the weight the spec
assigns. And `height_score` is derived from `avg_height_pct` — absolute line
*position*, not stability; the docstring at `:1052` says so outright ("measured
from actual average line height, not stability of movement"). A high, stable block
therefore scores as *not* compact.

As with A5, the emitted provenance string states the spec formula.

reasoned from a false scoreline.

**A8b — same defect, second site.** `pipeline_runner_v2.py:2229-2230` —
`wp → mc → 0`, never `match_boundaries.json`. Of the three readers of `ko_1h_s`,

## A11 — the spec does not bind steps to scripts (root cause of the drift class)

**Severity: HIGH (structural).**

`SKILL.md` defines 13 pipeline steps across 4,874 lines, mentions **8 distinct
script names** out of 43, and contains exactly **one** runnable command line
(`:3804`). **Steps 1, 1a, 1b, 1c, 1d, 1e, 1f and 2 name no script at all**;
**35 of 43 scripts are never referenced.** The binding survives only in module
docstrings, one-directionally (code → step), never spec → code.

Every finding in the historical `AUDIT.md` (F1-F5, F15) is a producer and consumer
disagreeing. Nothing declares which script is the producer for a step, so drift
has no point of detection — a step's spec can change with no script changing, and
a script can change without contradicting any written spec. A1, A2, A4, A5, A6 and
A8 are all fresh instances. `ARCHITECTURE.md`, delivered with this audit, supplies
the missing binding.

## A13 — the dual-agent merge silently drops match state on every event window

**Severity: HIGH.**

`merge_utils.py:490-561` builds its output as a **literal dict allowlist**.
Verified absent from it: `match_state`, `score_home`, `score_away`, `confidence`,
`source_limitations`, `timestamp_range`, `half` — all seven of which the agent
schema emits (`pipeline_runner_v2.py:440-445`, `:558-561`).

By contrast `merge_single_agent` (`:221-278`) starts from the whole parsed dict
and only *adds* keys, so **routine windows keep all seven**. Only event windows —
which take the dual path — lose them.

**Failure:** window 07 is a goal window, so an `agent_07_event.json` exists and
the dual path runs. Agent A emitted `"match_state": "away_winning"`. The merged
file has no `match_state` key, so `accumulator.py:477-494`'s `if ms:` is falsy and
**no row is appended**. On a 20-window match with 4 event windows,
`match_state_by_window` has 16 rows and the holes sit exactly at the goal windows —
the only windows where the score changes. `reconcile_goals_and_state`
(`:1719-1723`) back-fills only rows that exist, so the gaps persist into the report.

`half` survives via a fallback (`escalation_router._infer_half`, `:187-198`). The
other six have no consumer fallback.

## A14 — frame ordering assumes lexical == chronological; breaks at minute 100

**Severity: HIGH.**

Frames are named `f"frame_{m:02d}m{sec:02d}s.jpg"` (`window_plan.py:29-32`,
`detect_boundaries.py:171`). `{m:02d}` emits three digits past minute 99, and the
video clock includes pre-match and half-time, so a 90-minute match video routinely
runs 105–115 minutes.

`pipeline_runner_v2.py:198-201` and `:209-212` order frames with a plain
`sorted()` on filename. Verified:

```
sorted([...97m, 98m, 99m, 100m, 101m, 102m...])
  → ['frame_100m00s.jpg', 'frame_101m00s.jpg', 'frame_102m00s.jpg',
     'frame_97m00s.jpg',  'frame_98m00s.jpg',  'frame_99m00s.jpg']
```

**Failure:** a window spanning video 97m30s–102m30s is handed to the structural
agent as `[100m00s … 102m29s, 97m30s … 99m59s]`, while the prompt tells the agent
the frames are a chronological range (`:1051`). Every build-up chain,
`notable_shifts`, and inter-frame motion read for that window is sequenced
backwards — in second-half stoppage time and extra time, exactly where late
tactical shifts concentrate.

`detect_boundaries.py:455-457` sorts the same filenames with
`key=lambda p: frame_to_seconds(p)`, which is correct — confirming the runner's
lexical sort is an oversight, not a project convention.

## A15 — `datetime.utcnow()` on a deprecation path

**Severity: LOW.**

`setpiece_writeback.py:75, 119, 159, 196`. Deprecated from Python 3.12 and returns
a **naive** datetime; the appended `"Z"` asserts UTC by convention, not by value.
Use `datetime.now(timezone.utc)`. Environment is Python 3.11.15 — latent, not live.

## Architectural notes

- **`running_summary.json` has three live writers** (`accumulator.py:812`,
  `:1915`, `setpiece_writeback.py:181`), none atomic — plain `open(path,"w")` +
  `json.dump`. An interruption truncates the artefact every downstream stage reads.
  No concurrency exists today, so this is a durability risk, not a live race.
- **Two representations of kickoff** — nested `boundaries.ko_1h.seconds` in
  `match_boundaries.json` (written by code) vs flat `ko_1h_s`/`ht_s`/`ko_et1_s` in
  `match_config.json` (**no Python writer — hand-entered**). Direct cause of A8.
  `ht_s`, `ko_et1_s`, `ko_et2_s` have no writer anywhere.
- **158 of 1,245 dict keys are read by Python but never written by it** — they
  arrive from LLM agents following `SKILL.md`. A field can go missing because the
  spec changed, with no Python change and no test that would notice.
